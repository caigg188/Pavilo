# Pavilo 架构原则

Pavilo 是**浏览器即用、默认临时、可自托管、可按需组装的轻量聊天工具，也能为已有产品提供方便接入的聊天与玩法能力**。独立局域网工具与接入使用同一内核。接入不发布 SDK，契约见 [接入说明](../integrate.md)。

产品阶段以 [路线图](../../ROADMAP.md) 为准，当前模块见 [架构概览](overview.md)，目标见 [架构演进](../evolution.md)。新方向的决策记录是 [ADR-0008](../adr/0008-embeddable-composable-chat.md)。

## 七大不变量

### 1. Ephemeral First

默认安装和启动不需要数据库、账号系统、模型服务或第三方云服务。memory 模式默认不持久化，停止服务后聊天记录清空；SQLite 是明确选择的留存模式，不能把“重启清空”套用到 SQLite。

临时模式是完整产品模式。基础接入的身份验证不强制 SQLite；玩法当前要求 SQLite，是显式依赖，不代表所有功能都需要数据库。

### 2. One Mainline

独立页与嵌入页共用聊天内核、协议、客户端状态逻辑和发布主线，不维护两套产品。首期一个独立实例服务一个宿主应用，多频道不等于多租户隔离。

### 3. Optional Means Optional

能力按需启用，未开启时不强制第三方服务，不显著增加启动和认知负担。模块声明依赖并在启动/保存时校验，不承诺任意组合都有效。

实例管理存储、身份、网关和模块；频道管理功能和策略；服务端执行有效能力，UI 只负责呈现。隐藏按钮不是权限控制，SDK 不能开启服务端已关闭的能力。

### 4. Core Before Platform

内核小、确定、可测试；transport 处理网络，Store 处理存储，Gateway 处理模型 IO，Play 模块持有游戏规则。

```text
composition → transport / application → core / domain contracts
                          │                 │
                     IO adapters       Store port
```

禁止把 socket、HTTP request、SQL、厂商 SDK 或具体玩法规则放进领域内核。扩展的正常写入路径经过 core 命令，不直接写库或广播。客户端 reducer 不做 IO，独立页与 SDK 分别管理页面级副作用。

异步审核由应用编排承接，提交前复查身份、权限、频道状态和幂等；不为一个异步用例把全部领域规则改成异步，也不在网络等待期间持有写事务。

### 5. Compatibility Is a Feature

应用、配置、协议、数据库、未来 SDK 和扩展契约分别演进。v1.x 保持已承诺的 Protocol v4 与配置兼容；新能力尽量通过可选字段和能力协商加入。

v2.0 是稳定集成里程碑，允许必要的身份、配置或接口调整，但不人为制造破坏。每项不兼容变化有 ADR、迁移与回滚路径。现有冻结 Play 契约不能因新增 SDK 就被重新定义为不稳定内部接口。

### 6. Safe by Construction

身份、授权、审核分开；权限覆盖频道发现、历史与操作，不能只检查页面入口。用户、会话、连接和 Agent 席位分开；昵称不等于稳定身份。

当前部署仍面向可信 LAN、VPN 或有适当访问控制的私有网络。Origin 不是身份认证；反向代理本身不自动提供鉴权。嵌入只对指定入口开放来源，管理后台保持禁止嵌入，凭证不进 query 和路径。App 的 WebView 可以把凭证放进 fragment，页面会立刻删掉。

扩展是部署者信任的代码，不是沙箱。可捕获异常的隔离不等于可以约束无限循环、任意系统访问或进程退出。公网能力需通过身份、权限、TLS、可信代理、滥用防护和数据策略的实际验收。

### 7. No Premature Generalization

实际宿主接入和官方狼人杀驱动契约。维护者提供基础设施和完整参考，社区按同一规范扩展。狼人杀与接入并行，v2 前必须完成；不先造引擎、规则 DSL、市场或组件平台。

v2 暂缓无界面 SDK、深度组件替换、Node 后端包、动态建频道、完整账号系统、多租户、分布式存储和原生 SDK。外观优先品牌与布局配置。App 用系统 WebView 打开 `/embed`，不另做原生界面。

## 数据一致性

- memory 重启产生新 epoch；SQLite 正常重启保留 epoch/seq。
- SQLite 中消息与幂等记录同事务提交，commit 后才 ACK；ACK 不代表全员送达或已读。
- 内存工作集有界，容量淘汰不删除 SQLite 历史；留存删除后 seq 不复用。
- session、lease、typing、连接、心跳与缓冲属于运行时，不把 SQLite 当作网络会话恢复服务。
- 未来持久治理记录保存在 SQLite，临时治理状态遵守临时模式边界；管理员移除内容需同步历史、引用与在线视图。
- 人和 Agent 的公开消息统一经过权限、限额和审核；Play 私密状态只投递给授权演员。

## 测试与性能

优先 core 单元与契约测试，再用 transport 集成和浏览器验收覆盖真实边界。时钟、ID、定时器和外部 IO 可注入；不要用浏览器测试替代纯规则测试。

v2 增加能力关闭绕过、身份过期/切换、频道与历史越权、审核竞态、跨来源嵌入、SDK 重复挂载销毁和完整玩法验收。支持版本矩阵与关键浏览器检查必须阻塞发布；当前 CI 仍有允许失败项，应作为待完成工作说明。

先保证正确性与资源边界，再按可复现 benchmark 优化。对慢连接、存储、外部审核与事件队列设上限；不把未经实测的“高并发”或响应时间当成产品承诺。

## 文档与贡献

- README：中英文用户入口、当前能力与目标边界。
- 路线图：版本阶段、依赖、并行工作、发布门槛。
- 架构概览：当前实现；演进与集成设计：规划中的目标。
- 配置、协议、Play 文档：当前实际契约和可运行示例；未来字段不得混入。
- ADR：保留历史，对被替代内容明确链接后继决策。

新扩展、身份/授权端口或公共接口变化先说明实际用例与兼容影响。规划文档区分“已发布 / 主分支已实现 / 计划中”；文档修改本身不代表功能发布，也不要求自动改版本号。

## 代码审查检查清单

1. 默认临时用户是否被迫承担新的依赖或复杂度？
2. 能力和权限是否由服务端执行，依赖是否可验证？
3. 核心、网络、存储、厂商调用与玩法规则的边界是否清楚？
4. 身份变化、审核等待、提交失败、重启和超限的行为是否明确？
5. 人与 Agent 是否走统一治理路径，私密状态是否按接收者隔离？
6. 公共契约、兼容与迁移是否有对应测试？
7. 当前实现、规划、配置示例和中英文入口是否一致？

# Pavilo 架构演进

本文描述从独立聊天室到可组装、可嵌入聊天能力的演进方向，不是未来接口的使用说明。当前实现见 [架构概览](architecture/overview.md)，阶段见 [路线图](../ROADMAP.md)，宿主接入见 [集成设计（规划中）](integration.md)，决策见 [ADR-0008](adr/0008-embeddable-composable-chat.md)。

## 1. 当前基础与缺口

| 状态 | 架构基础 |
| --- | --- |
| v1.2.0 已发布 | 无网络聊天 core、HTTP/WS transport、客户端 protocol/connection/state/pending 分层、memory/sqlite ConversationStore、SQLite 运维 |
| v1.3.0 已发布 | 进程内 Gateway、operator 后台与配置覆盖层、席位禁言/请离/IP 黑名单、Play/Agent 宿主及 echo 夹具 |
| v1.4.0 已发布 | 功能目录、宿主 JWT 身份与频道授权 |
| v1.5.0 已发布 | 治理闭环：举报、墓碑移除、稳定 `userKey` 拒绝、操作记录。[ADR-0011](adr/0011-governance-loop.md) |
| v1.6.0 已发布 | 嵌入预览：宿主 iframe、`/embed`、玩法留在嵌入区域。[v1.6 设计](v1.6-design.md) |
| 进行中 | 一段话接入。不发布 SDK。[接入说明](integrate.md) |
| 计划中 | 提交前文本规则、通用 Policy/Event 扩展、官方狼人杀 |

当前 `server.js` 组合各模块，导入不会监听端口或注册信号。`createChatServer` 是现有工厂入口，不是装进对方 Node 应用的库。独立页仍以整站为中心，默认拒绝被嵌。配了 `embed.ancestors` 后，只有 `/embed` 和已启用玩法页可以被那些源嵌进 iframe。`embed.direct` 只让网页容器顶层打开 `/embed`，不因此允许被嵌。稳定用户拒绝是一份 `userKey` 名单，不是账号表；访客仍然没有可封禁的稳定身份。

可保留的基础是 command/effect 分离、同步领域规则、Store 端口、协议解析和客户端纯状态模块。不要通过复制第二套聊天实现来支持嵌入。

## 2. 目标架构与依赖方向

下面是目标职责图，不表示所有模块已经存在：

```text
独立聊天页 / 独立玩法页        宿主页面 + 网页容器
            │                      │
            │                 嵌入聊天 / 玩法页
            └──────────┬───────────┘
                  HTTP / WebSocket
                       │
          应用编排：身份 → 授权 → 能力 → 审核
                       │
             领域 core：命令 / 状态 / 事件
                 │                  │
        ConversationStore      提交后事件订阅
           memory/sqlite

Play host：持有具体对局规则，经受控命令路径公开发言
Gateway：服务端模型调用，由 Agent / 可选视觉审核使用
Operator：独立管理鉴权，经服务接口管理配置和治理
```

- Transport 负责连接、协议校验、容量和 effect 投递，领域规则留在 core/application。
- SQL、网络请求、厂商 SDK 不进入领域内核；Store 不负责向浏览器广播。
- 具体玩法规则、提示词与页面属于玩法目录，主线只提供契约与宿主。
- 客户端 reducer 保持纯函数；SDK 和独立页面各自管理宿主相关副作用，共用连接、协议、pending 和状态逻辑。
- 模块通过受控接口操作状态，不在正常扩展路径中绕过 core 直写 Store。可信代码具有进程权限，这条架构约束不是安全沙箱。

## 3. 独立使用与组装

临时模式与持久模式保持同一主线。默认启动不需要数据库、账号或模型服务。组装不是任意组合：实例声明存储、身份、网关和模块；频道声明功能、访问策略、审核和玩法；浏览器只提交使用意图。

服务端验证依赖并计算有效能力，UI 根据结果呈现。实例或频道关闭的能力不能被客户端开关、角色声明或扩展请求重新打开。图片、回复、回应、提及、输入提示与历史访问都需要对应服务端限制。

四类目标预设为临时聊天室、持久社区、嵌入聊天、聊天＋玩法。当前 Play 要求 SQLite，身份验证本身不强制持久化。不为适配尚不存在的数据库引入 ORM、Redis、远程存储或全面异步化。

## 4. 数据所有权与存储不变量

### 当前运行时与持久状态

运行时持有 socket/peer、在线成员、session/lease、typing、心跳、限流计数、pending 写缓冲和连接同步状态。SQLite 不保存可直接复活的网络连接或登录会话。

ConversationStore 管理消息、回复、回应、频道 epoch/seq 和幂等记录。SQLite 保存历史真源，内存是有界实时工作集；启动不能把全库历史读入内存。按容量淘汰工作集不等于删除 SQLite 历史，按留存策略删除历史后 seq 不复用。

- **memory**：进程重启产生新 epoch，历史清空；ACK 表示当前进程接受。
- **sqlite**：正常重启保留频道 epoch/seq；消息与幂等记录在同一事务中提交后才 ACK，失败不 ACK、不广播。数据库重置或替换必须考虑 epoch，不能把旧 pending 误发进新房间。
- 幂等键与原消息内容校验保持一致；身份接入后明确稳定用户和会话在键中的职责，不能仅替换用户名就宣称幂等迁移完成。
- 数据库迁移独立编号；单进程使用 SQLite，不支持多个实例共享同一个文件。备份、恢复、完整性检查和清理继续是发布回归项。

### 未来身份与治理状态

稳定用户和临时会话分离；宿主身份用于授权、历史归属和持久封禁，会话仍负责连接恢复。历史匿名消息不按同昵称自动绑定到新宿主账号；需要迁移时保留原作者信息并说明规则。

持久社区使用 SQLite 保存治理记录，临时模式不悄悄获得永久用户目录或审计记录。内容移除使用可同步标记，保证在线消息、分页历史、回复引用一致。对局与 Agent 私密记忆继续按游戏和演员隔离，不进入公共房间元数据。

## 5. 身份、授权与命令提交

身份验证回答“是谁”，授权回答“可以访问什么”，审核回答“内容能否提交”。宿主后端签发短期凭证，Pavilo 验证后建立身份上下文；昵称不是身份凭证。保留访客，但访客权限必须明确。

权限作用于频道发现、加入、历史、发送、受控互动与 Play 动作。续期、退出、身份切换、过期和重连必须检查当前身份与权限；operator token 不参与普通用户接入。

未来消息提交路径：

```text
验证身份 / 权限 / 能力 / 限额 / 输入 / 幂等
                    ↓
          可选异步 pre-commit 审核
                    ↓
  复查身份、权限、频道状态与幂等 → 事务提交
                    ↓
                 ACK / 广播
                    ↓
            有界 post-commit 事件队列
```

外部审核等待期间不持有 SQLite 写事务，不阻塞事件循环；使用应用编排承接异步 IO，保持可同步测试的核心规则。审核完成时命令所属会话、频道或权限可能已变化，必须复查，不能对旧上下文直接提交。

严格审核模式依赖失败、超时均拒绝；临时场景允许显式 fail-open。拒绝或未完成审核不得成功 ACK。人和 Agent 的公开消息经过同一套权限、限额、审核与持久化规则；Agent 无 peer 时按现有返回值报告结果，不虚构客户端 ACK。

## 6. 扩展职责与失败边界

| 扩展面 | 职责 | 失败行为 |
| --- | --- | --- |
| Identity | 验证宿主凭证，形成稳定用户上下文 | 无效或过期拒绝认证，不授予访客之外的权限 |
| Authorization | 判定频道可见性与操作权限 | 拒绝受控操作 |
| Policy | 提交前内容判定 | 明确超时与放行/拒绝策略，严格模式拒绝 |
| Event | 提交后订阅领域事件 | 不回滚消息；有队列上限、超时、日志 |
| Play | 状态机、合法动作、演员私密视图 | 可捕获错误标记该玩法故障，普通聊天保持可用 |

上表是目标职责，不是现有通用 Extension API。当前可用 Play API 见 [玩法契约](play.md)。新扩展提供声明、配置校验、生命周期与兼容测试；不使用一个万能 Hook 混合权限和游戏状态。

扩展是可信脚本。超时或 try/catch 能处理返回的 Promise 和可捕获错误，不能隔离无限循环、`process.exit`、恶意文件访问或进程资源耗尽。v2 不提供沙箱、热安装市场、任意代码上传或可靠外部消息总线。

## 7. Gateway 与 Play 并行演进

主分支网关提供服务端统一模型调用、渠道管理和用量；key 不进入公开元数据、浏览器或日志。普通聊天不依赖 AI。Agent 和未来可选视觉审核复用网关，不能让厂商 API 侵入 core。

当前 Play 绑定频道、拥有自己的页面、共用 Protocol v4 和会话；echo 是契约夹具，不是最终用户游戏。已冻结的 Play 契约按兼容承诺演进，新增端口必须由实际用例证明，并同步文档和测试。

官方狼人杀由协作者与主线并行开发，不占用 v1.5 或 v1.6 的维护者队列：规则由确定性状态机裁决，人和 Agent 混编，私密状态只给授权演员；覆盖完整对局、非法动作、断线恢复与模型失败。v2.0 冻结前必须有可运行对局。更多玩法由社区按照同一契约贡献。

嵌入模式中，聊天与玩法切换留在组件区域，不能跳走宿主应用。独立玩法页面不等于排斥主线提供统一 iframe 嵌入宿主；也不意味着把投票和夜间操作塞进聊天气泡。

## 8. 配置与版本演进

当前配置只使用已有 [配置契约](configuration.md)：Schema v1 为内存模式且禁止 `storage/operator/plays`；Schema v2 支持存储，operator/plays 要求 SQLite；`version: 3` 按 v2 读取。配置示例不提前加入身份或嵌入字段。

YAML 管启动与模块装载；房间、频道和治理配置按现有管理后台覆盖层认领；模型渠道只在后台配置。新字段的可编辑范围、来源和保存语义在相应实现 ADR 明确，不由 SDK 创造新的真源。

应用、配置 Schema、WebSocket、数据库迁移和未来 SDK/扩展契约独立编号。v1.x 继续兼容已有承诺。v2.0 为稳定集成能力允许集中架构调整，每项破坏性变更有具体依据、ADR、弃用和迁移说明，不预先杜撰 Protocol v5 或某个配置 Schema。

升级验证需包括旧数据库、旧配置、旧客户端失败提示和 SDK 版本范围。回滚通过兼容旧版本的数据格式或升级前备份完成，不假设迁移后的数据库可被任意旧版本读取。

## 9. 工程与文档验收

保留 core 单元、存储契约、网络集成、浏览器验收的层次；新增身份/权限、能力开关、异步审核竞态、SDK 生命周期、跨来源嵌入和 Play 私密状态测试。支持版本矩阵及关键浏览器检查在 v2 成为阻塞发布的门槛，不能把当前允许失败的 job 写成已经满足。

可观测性包括接入错误、审核延迟/超时、事件队列积压、模块故障和存储状态；不记录令牌、密钥、私密对局数据。性能以公开的容量边界和可复现基线说明，不宣称未经验证的并发数字。
